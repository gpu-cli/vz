# vz 1.0 Scope

Date: 2026-09-02
Status: future milestone context. The current 0.4 scope and completion contract
is [`../planning/developer-environments/GOAL-0.4.0.md`](../planning/developer-environments/GOAL-0.4.0.md); it supersedes conflicting single-Machine language here.

## Product definition

**vz creates reproducible, parallel Developer Environment topologies whose
Machines feel native to their target operating systems.**

A Developer Environment is an isolated realization of a project topology. A
project/worktree may have multiple Environment instances, and each Environment
owns one or more target-native Machines plus storage, networks, DNS, endpoints,
credentials, checkpoints, and lifecycle. Target OS and implicit Linux Docker
belong to each Machine, not the Environment aggregate.

Sandboxes, VMs, OCI containers, harness residency, pools, brokers, and socket proxies are implementation primitives or optional capabilities behind that object. They remain important APIs where advanced consumers need them, but they are not the center of the product story.

The primary value is reproducibility and safe parallelism on powerful local hardware. Lockdown is a selectable policy, not the default reason to use vz.

## Target contract and rollout order

Linux is the universal Machine target: every supported host eventually runs
Linux Machines. Native Machines complement Linux where the host supports them.

| Order | Host | Target | Scope | Developer Environment contract |
|---:|---|---|---|---|
| 1 | macOS | Linux | Immediate / 1.0 core | Reproducible Linux Machines, each with private Docker driven by the Mac Docker CLI |
| 2 | macOS | macOS | Immediate / 1.0 core | Native macOS Machines for Xcode, Swift, Darwin, Homebrew, and mixed-target topology |
| 3 | Linux | Linux | Next | The same Linux environment contract using native Linux isolation |
| 4 | Windows | Linux | Then | The same Linux environment contract on Windows, using the appropriate Windows virtualization backend |
| 5 | Windows | Windows | Final | Native Windows Developer Environments for Windows toolchains and workloads |

This order is contractual. It prevents “cross-platform” from becoming an ambiguous promise and makes Linux portability explicit from the beginning. Native macOS is back in immediate scope; native Windows is the last target in the declared sequence.

## The topology experience

On macOS, a project declares Linux and/or macOS Machines and operates the
Environment through the same five-verb lifecycle:

```text
vz up --environment <name>
vz exec --environment <name> --machine <name> -- <command>
vz status --environment <name> --json
vz stop --environment <name>
vz delete --environment <name>
```

The object model is fixed: one project/worktree can own multiple independently
addressable Environments, and each Environment can contain multiple Machines.

Creating a Linux Machine implicitly provisions its Docker capability. Each Linux
Machine owns its Engine, containerd, BuildKit state, images, volumes, networks,
endpoint, and context. The unmodified host Docker CLI selects that exact
Environment/Machine. No Environment-global or global vz daemon exists.

Creating a macOS Machine provisions native execution. It can communicate with a
declared Linux Machine but never inherits that Machine's Docker capability.

## Definition of done

1. macOS operates multi-Machine and mixed Linux/macOS Environment topologies
   through one coherent lifecycle.
2. Multiple Environments per project/worktree and multiple Machines per
   Environment run concurrently with deterministic identity and isolation.
3. Linux-on-macOS Docker compatibility is Machine-local and exercised end to end
   from the unmodified Docker CLI, Compose, and buildx on the Mac.
4. Native macOS environments support real Apple-platform development workflows and document hardware-bound image/save-state constraints honestly.
5. CLI, Rust, gRPC, events, `--json`, and capability reporting agree on
   Project/Environment/Machine identity, Machine target OS, topology, lifecycle,
   and target-qualified capabilities.
6. Release claims are backed by local end-to-end evidence on the declared
   host×Machine-target pair, not only unit tests or mocked backends.

## Must ship

- First-class Project, `DeveloperEnvironment`, and Machine contracts with stable
  identities, per-Machine target OS/capabilities, workspace bindings, topology,
  lifecycle, and machine-readable status.
- macOS→Linux and macOS→macOS Machine backends behind that contract, including
  a mixed-target Environment.
- Parallel creation across projects/worktrees/Environment instances and Machines
  with bounded allocation and collision-free owned resources.
- Reproducible environment definitions, pinned/checksummed artifacts, version reporting, repair, upgrade, and clean rebuild behavior.
- Machine-local Docker for Linux targets: dockerd, containerd, BuildKit,
  youki-only OCI execution, networking, persistence, per-Machine host
  endpoint/context, Compose, buildx, and exhaustive Mac-driven E2E coverage.
- Native macOS provisioning and execution: pinned restore/install inputs, project mounts, guest tooling, lifecycle, recovery, and Apple-platform E2E workflows.
- Streaming exec, stdin/PTY/signals/resize/cancellation, file transfer, port forwarding, events, leases, resource limits, TTL, checkpoints where the backend supports them, and explicit capability downgrade where it does not.
- Brokered credentials and explicit workspace/network policy as Environment and
  Machine capabilities. Use is attributable to the exact identity.
- Universal structured output, stable exit codes, versioned errors, and an agent-friendly skill over the same control-plane truth.
- Published host×Machine-target capability profiles. A backend reports
  capabilities; callers do not infer them from the host name.

## Target-qualified Docker acceptance

For macOS→Linux, acceptance means a user selects one Linux Machine's generated
Docker context and uses normal host `docker`, buildx, and Compose commands. Two
Linux Machines in one Environment and Machines in separate Environments must
work concurrently and remain isolated. Evidence proves the exact selected
Machine handled the request and no fallback daemon was used.

Docker parity claims apply to this Linux Machine target only until the same suite
passes on another host×Machine-target pair. The required lane is
`scripts/run-linux-docker-e2e.sh --suite all`, run from the host against
release-built artifacts with execution-derived youki-only proof.

## Capability, not product center

Agent harness residency remains valuable: an environment may host Claude Code, Codex, OpenCode, or another harness with identity-preserving state and brokered credentials. Worktree sessions and a locked-down exec zone remain supported patterns. They are capabilities of a Developer Environment, not a separate destination that delays the core environment contract.

Likewise, a hardened container/sandbox profile remains available for workloads that value restriction over compatibility. It must not dictate defaults for the Developer profile or weaken the full Docker and development experience.

## Deferred by rollout order

- Linux→Linux conformance is the first post-1.0 host expansion.
- Windows→Linux follows using the same Linux target contract and conformance suite.
- Windows→Windows is the final native-target expansion.
- Hosted fleet scheduling, multi-tenant control planes, marketplaces, MCP adapters, and orchestrator attempt graphs remain outside the local Developer Environment contract.

## Historical decision note

Earlier plans centered the product on “the agent lives in the sandbox,” cut
native macOS guests from 1.0, and treated Docker as a global facade. The current
contract supersedes those calls: reproducible parallel Environment topologies
are primary; native macOS Machines are immediate; Linux is the universal
cross-host Machine target; and Docker is implicit per Linux Machine.
