# vz 1.0 Scope

Date: 2026-09-02
Status: committed scope. Beads carry implementation work; this document carries product decisions.

## Product definition

**vz creates reproducible, parallel Developer Environments that feel native to their target operating system.**

A Developer Environment is the user-facing object. It owns a project identity, target OS, compute boundary, filesystem state, tools, services, ports, credentials policy, checkpoints, and lifecycle. Users create, start, enter, stop, clone, and delete Developer Environments; they should not have to assemble a VM, sandbox, container, Docker daemon, or harness residency configuration first.

Sandboxes, VMs, OCI containers, harness residency, pools, brokers, and socket proxies are implementation primitives or optional capabilities behind that object. They remain important APIs where advanced consumers need them, but they are not the center of the product story.

The primary value is reproducibility and safe parallelism on powerful local hardware. Lockdown is a selectable policy, not the default reason to use vz.

## Target contract and rollout order

Linux is the universal target: every supported host eventually runs Linux Developer Environments. Native targets complement Linux where the host can support them; they do not replace it.

| Order | Host | Target | Scope | Developer Environment contract |
|---:|---|---|---|---|
| 1 | macOS | Linux | Immediate / 1.0 core | Reproducible parallel Linux environments, including an environment-local Docker Engine driven by the Mac Docker CLI |
| 2 | macOS | macOS | Immediate / 1.0 core | Native macOS environments for Xcode, Swift, Darwin binaries, Homebrew, and Apple-platform work |
| 3 | Linux | Linux | Next | The same Linux environment contract using native Linux isolation |
| 4 | Windows | Linux | Then | The same Linux environment contract on Windows, using the appropriate Windows virtualization backend |
| 5 | Windows | Windows | Final | Native Windows Developer Environments for Windows toolchains and workloads |

This order is contractual. It prevents “cross-platform” from becoming an ambiguous promise and makes Linux portability explicit from the beginning. Native macOS is back in immediate scope; native Windows is the last target in the declared sequence.

## The 1.0 experience

On macOS, a project can select `linux` or `macos` and then use the same lifecycle:

```text
vz dev create --target linux
vz dev start
vz dev enter
vz dev stop
vz dev clone <new-name>
```

Exact command spelling may evolve, but the object model must not: one project can own multiple independently addressable Developer Environments, and multiple environments must run concurrently without sharing mutable state accidentally.

Creating a Linux Developer Environment implicitly provisions its Linux development services, including Docker compatibility. There is no global vz Docker daemon. Each Linux environment owns its own Engine, containerd, BuildKit state, images, volumes, networks, endpoint, and Docker context. The unmodified host Docker CLI selects that particular environment. A target that does not advertise Docker support must fail clearly; “Docker compatible” is never an unqualified property of every target OS.

Creating a macOS Developer Environment provisions native macOS execution. Docker remains a capability of a selected Linux environment, not a hidden global service and not a claim that macOS guests run a native Docker Engine.

## Definition of done

1. macOS can create, run, clone, checkpoint where supported, stop, recover, and delete both Linux and native macOS Developer Environments through one coherent lifecycle.
2. Multiple environments can run in parallel with deterministic project identity and no cross-environment leakage of files, processes, sockets, ports, caches, credentials, or lifecycle events.
3. Linux-on-macOS Docker compatibility is environment-local and is exercised end to end from the unmodified Docker CLI, Compose plugin, and buildx plugin on the Mac.
4. Native macOS environments support real Apple-platform development workflows and document hardware-bound image/save-state constraints honestly.
5. CLI, Rust, gRPC, events, `--json`, and capability reporting agree on environment identity, target OS, lifecycle, and available target-qualified capabilities.
6. Release claims are backed by local end-to-end evidence on the declared host/target pair, not only unit tests or mocked backends.

## Must ship

- A first-class `DeveloperEnvironment` contract with stable identity, explicit host and target OS, project binding, profile, lifecycle, state paths, capabilities, and machine-readable status.
- macOS→Linux and macOS→macOS backends behind that contract.
- Parallel creation and execution with bounded resource allocation and collision-free disks, mounts, sockets, ports, checkpoints, logs, and credentials.
- Reproducible environment definitions, pinned/checksummed artifacts, version reporting, repair, upgrade, and clean rebuild behavior.
- Environment-local Docker for Linux targets: dockerd, containerd, BuildKit, youki-only OCI execution, networking, persistence, per-environment host socket/context, Compose, buildx, and exhaustive Mac-driven E2E coverage.
- Native macOS provisioning and execution: pinned restore/install inputs, project mounts, guest tooling, lifecycle, recovery, and Apple-platform E2E workflows.
- Streaming exec, stdin/PTY/signals/resize/cancellation, file transfer, port forwarding, events, leases, resource limits, TTL, checkpoints where the backend supports them, and explicit capability downgrade where it does not.
- Brokered credentials and explicit filesystem/network policy as environment capabilities. Secrets remain host-controlled and use is attributable to one environment.
- Universal structured output, stable exit codes, versioned errors, and an agent-friendly skill over the same control-plane truth.
- Published host×target capability profiles. A backend reports capabilities; callers do not infer them from the host name.

## Target-qualified Docker acceptance

For macOS→Linux, acceptance means a user can select one specific Developer Environment with a generated Docker context (or environment emitted by vz) and use normal host commands such as `docker ps`, `docker buildx build`, and `docker compose up`. Two environments must work concurrently and remain isolated. Tests must prove that requests reached the selected vz environment and never Docker Desktop, another environment, or a fallback daemon.

Docker parity claims apply to this Linux target only until the same suite passes on another host×target pair. The required lane is `scripts/run-linux-docker-e2e.sh --suite all`, run from the host against release-built artifacts, with execution-derived proof that youki is the only OCI runtime present and invoked.

## Capability, not product center

Agent harness residency remains valuable: an environment may host Claude Code, Codex, OpenCode, or another harness with identity-preserving state and brokered credentials. Worktree sessions and a locked-down exec zone remain supported patterns. They are capabilities of a Developer Environment, not a separate destination that delays the core environment contract.

Likewise, a hardened container/sandbox profile remains available for workloads that value restriction over compatibility. It must not dictate defaults for the Developer profile or weaken the full Docker and development experience.

## Deferred by rollout order

- Linux→Linux conformance is the first post-1.0 host expansion.
- Windows→Linux follows using the same Linux target contract and conformance suite.
- Windows→Windows is the final native-target expansion.
- Hosted fleet scheduling, multi-tenant control planes, marketplaces, MCP adapters, and orchestrator attempt graphs remain outside the local Developer Environment contract.

## Historical decision note

Earlier plans centered the product on “the agent lives in the sandbox,” cut native macOS guests from 1.0, and treated Docker as a facade spanning macOS and Linux hosts. Those decisions captured useful broker, residency, conformance, and runtime work, but the product priority has changed. This document supersedes those scope calls: reproducible parallel Developer Environments are primary; native macOS is immediate; Linux is the universal cross-host target; and Docker is an implicit, per-environment capability of Linux Developer Environments.
