# vz 2.0 Vision — Harness Residency

Date: 2026-09-02
Status: design spec for the harness-residency destination. **Harness Residency v1 is the 1.0 capstone (see `docs/1.0-scope.md`); this doc is the full destination beyond it.**
Companion: `docs/1.0-scope.md` (the 1.0 contract this builds on).

## The narrative

**1.0 protects the host from the agent. 2.0 makes the sandbox the agent's home — and the host becomes the peripheral.**

- 1.0: the agent *uses* vz from outside. Risky work is pushed into the sandbox through explicit verbs (`vz run`). The boundary is opt-in.
- 2.0: the agent *lives* in vz. The harness itself runs in the sandbox with the same memory, history, tools, and capabilities the user has on macOS. The boundary is the default state; the host is opened deliberately — for git truth, credentials, and review.

A real agentic workflow must not be a downgrade inside vz. Claude Code needs its memory. `bd` needs to push. `gh` needs auth. `git` needs identity. 2.0 ships that with zero credentials crossing the boundary.

## The shift in one table

| | 1.0 | 2.0 |
|---|---|---|
| Agent location | host, calls into sandbox | harness resident in sandbox |
| Boundary | opt-in per command | default state; host opened deliberately |
| Memory/history | not the sandbox's business | identity-preserved, live, resumable |
| Credentials | absent from guest | brokered — usable, never readable |
| Session object | sandbox | worktree (one worktree = one sandbox = one agent) |

## Architecture

```
HOST (macOS)                          GUEST VM (per worktree session)
──────────                            ─────────────────────────────────
myrepo/.git/worktrees/feat-x  ──RW──► /Users/james/myrepo  (IDENTITY-PRESERVING
                                      path — same path key the harness uses)
~/.claude/projects/<proj>      ──RW──► ~/.claude/projects/<proj>   (live history)
~/.claude/CLAUDE.md (memory)    ──RW──► same file, both sides
~/.claude/settings.json        ──RO──► tamper-proof settings
~/.gitconfig                   ──RO──► identity (name/email)
vz-toolbox image (gh, bd, git) ──RO──► pinned Linux binaries
Keychain / ssh-agent / gh token  ─X─►  NEVER CROSSES
                                             │
                       ┌─────────────────────┴──────────────┐
                 HARNESS CONTAINER                   EXEC ZONE (bwrap)
                 (trusted compute)                   (untrusted compute, per-cmd)
                 claude + toolbox                     sees /workspace only —
                 profile mounts                      no ~/.claude, no creds,
                 HTTPS_PROXY / SSH_AUTH_SOCK          no broker env
                 = vsock-backed shims
                       │
   per-sandbox BROKER (host side, vz-runtimed)
     credential providers: ssh-agent signer · gh token · Keychain · env · 1Password CLI
     audit log: every signature, every token use, attributable per sandbox
     policy: rate limits, operation allowlists (e.g. "may sign pushes for this remote only")
```

## Trust model

Two trust zones per session; **zero credential bytes in the guest, ever.**

1. **Harness zone** (youki container): harness binary + state mounts + broker shims. Trusted compute — but still prompt-injectable, so it holds no secrets, only doors.
2. **Exec zone** (bubblewrap, per command): the agent-installed code the harness executes. Sees the worktree only. Provisioned so the harness's own native sandboxing (e.g. Claude Code's bwrap mode) works out of the box; the VM remains the backstop if process-level isolation fails.

Trust classes are different things: **state** (memory, history, repo data) mounts; **credentials** broker. A compromised exec zone or harness can *use* an authenticated channel (visible in the broker audit log) but can never *read* the credential.

## Components

### 1. Worktree-as-session (the session object)

Two modes, one contract:

- **Create mode (solo UX):** `vz sandbox spawn --worktree feat-x` atomically creates a host worktree + a sandbox. Identity, naming, and namespace-collision handling already exist (`crates/vz-cli/src/commands/sandbox.rs`: `SpaceWorktreeIdentity`, collision guard). Rules: one worktree = one sandbox = one agent session, enforced; branches are parallel by construction; cleanup = `git worktree remove` + `vz sandbox rm`. `git worktree list` on the host shows live agent sessions.
- **Attach mode (orchestrator-driven):** `spawn --worktree <existing-path>` binds a sandbox to a worktree the orchestrator already created and owns. vz attaches execution to it (mounts, sandbox, checkpoint scope) and never creates, deletes, or mutates git objects on the orchestrator's behalf. This is the mode external control planes (e.g. prtl) use — they own worktree lifecycle, vz owns execution (see `docs/session-executor-contract.md`).

Mount model (both modes): repo root read-only (history readable) + worktree read-write (commits land in the host's object DB through the worktree). Git commits happen *natively inside* — no boundary verbs, no honor system. Push auth is brokered (below). Credentials never enter the guest; pushes are signed by the host's ssh-agent through the shim.

### 2. Identity-preserving mounts

The identity problem: harnesses key state by absolute project path (Claude Code: `~/.claude/projects/-Users-james-myrepo/`). Fix: mount the worktree inside the guest at its **host-absolute path**. The harness then reads/writes the same key it uses on macOS; since `~/.claude/projects` is a live RW mount, it is literally the same `.jsonl` files. `claude --resume` shows real host sessions. No sync, no seeding, no merge.

### 3. Harness residency manifests

Per-harness, per-version declarative spec of the `~` surface, with four treatments:

| Treatment | Meaning | Examples |
|---|---|---|
| `mount-rw` | live shared bytes | project history, user memory (`~/.claude/CLAUDE.md`), repo-borne state (`.beads/` rides the worktree) |
| `mount-ro` | readable, tamper-proof | `settings.json`, `~/.gitconfig`, dotfiles, pinned tool binaries |
| `broker` | usable, never readable | LLM API keys, gh token, ssh-agent, git credentials |
| `fresh` | synthesized per VM | everything else in `~`; dies with the sandbox |

`vz sandbox spawn --harness claude` consumes a manifest. Manifests are **data, not code**, versioned against harness releases (harness state layouts churn; manifests must track them without vz releases).

### 4. The shim/broker protocol (proven pattern, formalized)

The boundary mechanism — already proven ad-hoc in this project (shim mounted in sandbox, vsock to host) and production-shaped in-tree (`Vm::vsock_connect(port)` in `crates/vz/src/vm.rs`, buildkit bridge on 7425):

- **Shims**: unix sockets synthesized in the guest at stable paths (`/run/vz/shims/ssh-agent.sock`, `/run/vz/shims/https-proxy.sock`, git credential helper). Tools find auth exactly where they expect it (`SSH_AUTH_SOCK`, `HTTPS_PROXY`, credential-helper config). Unmodified tools; no special modes.
- **vsock port registry**: 7424 guest agent · 7425 buildkit · reserve 7426+ for per-provider broker channels. One table in the runtime contract; shims never collide.
- **Broker**: per-sandbox instance in vz-runtimed, with pluggable credential providers (host ssh-agent signer, gh token, Keychain item, env token, `op` CLI), an audit log of every use, and policy (per-sandbox identity, rate limits, operation allowlists such as "this sandbox may sign pushes for this remote only").
- The broker is also the natural interception point for egress policy (same socket discipline as `vz-xym`).

### 5. Toolbox images

`vz-toolbox`: pinned Linux binaries for the tools agents actually drive (gh, bd, git, kubectl, ...). Tool *config* mounts RO; tool *auth* brokers; tool *state* mounts RW or rides the repo. Version pinning matters: the toolbox is an image, refreshed deliberately, cached per profile.

### 6. Session-scoped project history

The genuinely novel problem: Claude Code assumes one live project-state directory. Five parallel agents RW-mounting the same `~/.claude/projects/<proj>` would clobber each other. Default: **user-level memory shared RW; project history session-scoped per worktree**, with an explicit opt-in for shared project state and a host-side "merge memories" step. This must be a conscious spec decision, not an accident of mounting.

## What 2.0 is explicitly not

- Not boundary verbs. Native `git`/`gh`/`bd` work unmodified; the boundary is the socket, not a verb surface.
- Not credentials in the guest. Not ever.
- Not hosted sandboxes, not MCP, not the deferred platform list from 1.0-scope.
- Not a trust claim that the harness can't be prompt-injected into *using* its channels — the broker sees and limits that; no filesystem design prevents it.

## Dependencies on 1.0 (why 2.0 waits)

Files API (`vz-dko`) · multi-project concurrency (`vz-767`) · egress policy + broker infra (`vz-xym`) · `CONFIG_USER_NS` kernel work (shared with rootless dockerd, `vz-avq`/`vz-5in`) · multi-sandbox lifecycle (`vz-305`).

## Risks

1. **Harness-internal churn** — state layouts and sandboxing modes change; manifests are versioned data to absorb this.
2. **Memory-model novelty** — session-scoped history has no upstream precedent; needs real multi-agent testing.
3. **bwrap quality is process-level**, not VM-level — the VM is the backstop; don't oversell exec-zone isolation.
4. **Case sensitivity** — host APFS case-insensitive vs guest case-sensitive; document the worktree-mode caveat.
5. **Keychain doesn't cross** — by design; the broker *replaces* it. Failure mode if the broker is missing: capability downgrade (the exact problem 2.0 exists to solve).

## The 2.0 demo

> Type `claude` in a worktree. vz spawns a VM, mounts your identity (same history, same memory, same settings), runs the harness in a container, brokers your credentials (LLM API, gh, ssh), and every command the agent executes is trapped inside. It commits into your real repo and pushes through your host's ssh-agent — the key never left your Mac. `--resume` on the host continues the conversation. Exit → VM dies → nothing touched your Mac except the worktree and git objects.

Five worktrees, five harnesses, five isolated histories, one host object DB.
