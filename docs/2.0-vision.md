# vz 2.0 Vision — Universal Developer Environments

Date: 2026-09-02
Status: design direction beyond the macOS-first 1.0 scope.
Companion: `docs/1.0-scope.md`.

## The narrative

**vz makes reproducible, parallel Developer Environment topologies local and
native-feeling on every major host. Linux is the universal Machine target;
native Machines are added where the host supports them.**

The product is an Environment topology, not a hypervisor wrapper or sandbox
command. A project defines Machines and networks, instantiates that definition
many times, and drives normal tools from the host. Each instance can contain
heterogeneous target-native Machines.

The rollout is intentionally asymmetric:

1. macOS host → Linux target
2. macOS host → macOS target
3. Linux host → Linux target
4. Windows host → Linux target
5. Windows host → Windows target

Linux is the common target on macOS, Linux, and Windows. Native macOS and native Windows targets serve development that genuinely requires their platform toolchains. vz does not pretend that every target has identical mechanics; it provides one lifecycle and reports target-qualified capabilities honestly.

## One aggregate, heterogeneous Machines

Every Developer Environment has:

- a stable identity and human name;
- a project binding and reproducible definition;
- one or more Machines with explicit target OS, architecture, and backend;
- isolated mutable state, resources, endpoints, logs, events, and credentials policy;
- lifecycle operations with consistent semantics;
- a versioned capability report;
- optional resident services and harnesses selected by target and profile.

The implementation can be a Virtualization.framework VM, native Linux namespaces/cgroups, a Windows virtualization backend, or a native Windows isolation backend. Backend names must not leak into ordinary workflows where a capability suffices.

## Host×Machine-target architecture

| Host→target | Isolation/backend direction | Core target experience |
|---|---|---|
| macOS→Linux | Apple Virtualization.framework Linux VM | Universal Linux toolchain; per-Machine Docker |
| macOS→macOS | Apple Virtualization.framework macOS VM | Xcode, Swift, Darwin, Homebrew, Apple SDKs |
| Linux→Linux | Native Linux isolation, with VM-grade backend where requested | Same Linux definition and Docker contract |
| Windows→Linux | Windows-hosted Linux virtualization | Same Linux definition and Docker contract |
| Windows→Windows | Native Windows virtualization/isolation | Windows SDK, MSVC, PowerShell, Windows services |

Capability reports describe differences such as checkpoint portability, nested
virtualization, GPU access, filesystem semantics, networking, and Docker.
Conformance evidence is host×Machine-target qualified; one pair never certifies
another.

## Linux as the universal target

The Linux Machine definition is the portable center of the system. The same
project topology intent—Machines, artifacts, packages, files, services,
resources, mounts, networks, endpoints, and policies—must travel from
macOS→Linux to Linux→Linux and Windows→Linux. Backend fields are explicit
capability-conditioned extensions.

Docker compatibility is implicit for the Developer profile of every supported
Linux Machine. It is Machine-local and target-qualified:

- each Linux Machine owns its own dockerd, containerd, BuildKit state, images,
  volumes, networks, credentials, endpoint, and Docker context;
- the unmodified host Docker CLI, Compose, and buildx select one
  Environment/Machine explicitly;
- vz never installs a global daemon, changes the user's default Docker context, or falls back to Docker Desktop/system Docker;
- stopping one Machine cannot disturb siblings or other Environments; deleting
  an Environment removes all and only its Machine contexts/state;
- the identical behavior suite is rerun on each Linux host×Machine-target pair
  before parity is claimed there.

Native macOS and native Windows Machines do not inherit a Docker claim from
Linux Machines in the same or another Environment.

## Parallelism and reproducibility

Parallelism has two axes: many independent Environment instances and several
cooperating Machines inside each instance. A high-memory workstation should host
both without accidental coupling. Reproducibility includes more than rebuilding
a root filesystem:

- deterministic identity and configuration resolution;
- pinned, checksummed system and tool artifacts;
- explicit persistent versus disposable state;
- collision-free disks, mounts, namespaces, sockets, ports, caches, logs, and process ownership;
- bounded CPU, memory, disk, and lifecycle leases;
- transactional create/upgrade/repair/delete operations;
- exportable definitions and machine-readable provenance;
- clean-state and persisted-state conformance runs.

## Native target experiences

### macOS

Native macOS returns to immediate product scope because Linux cannot replace Xcode, SwiftUI previews, Darwin builds, Apple SDKs, or macOS-specific validation. Apple constraints—IPSW installation, signing, sudo during provisioning, Secure Enclave-bound save state, VM-count limits, and non-portable checkpoints—must be exposed as capabilities and documented, not used to hide the target.

### Windows

Native Windows is the final declared target. It should reuse environment identity, lifecycle, policy, brokers, events, and reproducibility contracts while implementing Windows-native filesystems, services, process isolation, credentials, and toolchains. The design must leave room for it now without pretending its backend is already specified.

## Harness residency as a capability

An environment may run an agent harness inside its boundary so the agent's commands execute there by default. The valuable mechanisms from the earlier Harness Residency design remain:

- identity-preserving project/worktree mounts;
- versioned per-harness state manifests;
- brokered SSH, GitHub, package, and model credentials whose bytes remain host-controlled;
- pinned toolbox artifacts;
- session-scoped histories for parallel agents;
- an optional stricter exec zone inside the environment;
- auditable use of host-side capabilities.

These mechanisms enrich Developer Environments; they do not redefine the environment as “a sandbox for an agent.” Humans, IDEs, scripts, CI jobs, and external orchestrators use the same environment contract.

## Historical residency architecture, retained

The previous design used “one worktree = one sandbox = one agent” and placed a harness container plus a bubblewrap exec zone inside a per-worktree Linux VM. It mounted worktrees at host-absolute paths so harness history keys remained stable, shared selected state read/write, mounted settings read-only, and exposed credentials only through vsock-backed shims and a per-environment broker.

That remains a strong implementation pattern for the resident-harness capability. Terminology changes as follows:

| Historical term | Current interpretation |
|---|---|
| Sandbox/session as product object | Developer Environment, optionally bound to a worktree |
| Per-sandbox broker | Per-environment broker identity |
| Harness-in-sandbox destination | Optional resident-harness capability |
| Sandbox profile | Environment policy/profile |
| Worktree = sandbox | A useful parallel-session convention, not a universal identity rule |

## Control-plane boundary

vz owns local environment execution: identity, provisioning, lifecycle, mounts, resources, transport, services, capabilities, policies, brokers, checkpoints, files, ports, and evidence. It does not own task graphs, model selection, retries/attempt semantics, fleet scheduling, or an orchestrator's evidence database. External control planes compose environments through the generic contract in `docs/session-executor-contract.md`.

## Success criteria

1. A Linux Machine definition and its Environment topology have equivalent
   lifecycle and exhaustive conformance on macOS, Linux, and Windows hosts.
2. macOS hosts also provide production-quality native macOS environments.
3. Windows hosts ultimately provide native Windows environments without fragmenting the contract.
4. Parallel Environments and multi-Machine/mixed-target topologies have
   demonstrable isolation and reproducibility under stress and failure.
5. Docker claims are made only for tested Linux Machine host×Machine-target pairs and
   are driven by the host's normal Docker tools against each exact Machine.
6. Harnesses and orchestrators can live inside or drive an environment without becoming product-specific concepts in core APIs.

## Risks

1. **False portability:** common nouns can conceal materially different semantics. Capability reporting and pair-specific conformance must fail closed.
2. **Filesystem differences:** APFS, Linux filesystems, VirtioFS, NTFS, case sensitivity, permissions, symlinks, and locking require explicit contracts.
3. **Artifact supply:** Linux, macOS, and Windows installation/update channels have different licensing, signing, and redistribution constraints.
4. **Parallel resource pressure:** large local machines invite high concurrency; admission, quotas, cleanup, and observability must be designed rather than bolted on.
5. **Docker overclaiming:** Engine/API compatibility on one Linux backend does not prove parity on another.
6. **Credential boundary variance:** Keychain, ssh-agent, Linux keyrings, and Windows credential providers require a common broker contract with target-specific implementations.
