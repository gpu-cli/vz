Features

  • ▪Real isolation, not seatbelt. Full Linux VM per sandbox via Apple Virtualization.framework1
  • ▪~3 s cold boot to first command, warm reuse thereafter2
  • ▪Host stays clean. Zero workload processes on macOS, including the Docker daemon itself3
  • ▪Agent-native interface. MCP tool register, streaming exec, file API, signed receipts4
  • ▪Containers in the guest. OCI images via youki; deterministic Compose stacks; BuildKit builds
  • ▪Disposable by design. Checkpoint, restore, fork, destroy: a sandbox costs nothing to throw away
  • ▪Local-first, cloud-optional. Same runtime contract when Linux hosts arrive later

1 · General description

vz is a local-first sandbox runtime for the way software is written in 2026: an agent that compiles, installs, executes, and exfiltrates, inside a Linux VM that boots in about three seconds, mounts your project through VirtioFS, and never lets a single instruction touch macOS.3

An agent's riskiest command becomes a non-event. The host effect is NONE — no host processes, no host files, no host sockets. And when the run is over,, the sandbox is checkpointed, restored, or destroyed in one command.

vz is one CLI for three runtimes: OCI containers (youki, in-guest), Compose-class stacks (deterministic reconciler), and raw Linux VMs (custom 6.12.85 kernel, two profiles)5. The control plane (a gRPC daemon and local HTTP API) is built for orchestrators: leases, events, receipts, capability negotiation.4

Revision F specifies the future state this document sells: the runtime data plane completed (streaming exec, file API), full Docker compatibility with the daemon living inside the guest3, and the MCP register map of §4. Each table below carries its honest status.

Status vocabulary: ACTIVE shipped in v0.3.20 · DEV in development · PLANNED committed roadmap, subject to change.

5Detailed description

Clauses 5.1 – 5.6
5.1Host / guest boundary

The host runs a CLI, a control daemon, and thin vsock/VirtioFS plumbing. The guest runs everything else. This is not a Docker Desktop arrangement in disguise: there is no hidden VM doing unaccountable work; the VM is the product, inspectable down to its kernel config.3

Status: ACTIVE architectural invariant since v0.1
5.2Container runtime & stacks

OCI images pull, run, exec, and log through youki executing inside the guest; the host never unpacks a layer. Compose-class stacks reconcile deterministically through vz-stack: same apply, same result, restart-safe.

# bring a whole environment up, stream its logs, tear it down
vz stack up -f compose.yaml -n demo
vz stack logs demo --service web --follow
vz stack down demo --volumes
Status: ACTIVE youki in-guest · ACTIVE deterministic stacks · DEV stack egress (netns MASQUERADE)
5.3Docker compatibility: the daemon lives in the guest

Revision F's headline: run the real Docker inside the guest. dockerd + containerd execute in the VM on the guest kernel (MEMCG and BRIDGE_NETFILTER enabled); the host gets a unix-socket proxy over vsock. Your existing docker CLI, Compose, and buildx work verbatim, pointed at a daemon your Mac never ran.3

# nothing changes except where the daemon lives
export DOCKER_HOST=unix://$HOME/.vz/docker.sock
docker compose up
docker build -t app .
Status: ACTIVE vz docker shim (run/exec/ps/logs/pull/build, strict guardrails) · PLANNED full dockerd-in-guest + socket proxy
5.4Agent integration & trust

Beyond the MCP register of §4, every mutating operation emits a signed receipt; an orchestrator can reconstruct exactly what an agent did, when, and to which sandbox. Leases and events are first-class in the gRPC contract.

Status: ACTIVE receipts + leases in runtime contract · DEV inspection surface · PLANNED MCP server
5.5Checkpoints & disposability

fs_quick snapshots capture workspace state in seconds; restore forks a sandbox from any checkpoint. The unit of agent experimentation becomes cheap: try the dangerous thing, restore, try again. macOS guests additionally support full save/restore VM state.

Status: ACTIVE fs_quick (daemon) · ACTIVE macOS VM save/restore · PLANNED template-from-checkpoint
5.6Platform expansion

Same CLI, same runtime contract, Linux hosts later: sandboxes become containers on a native kernel, no workflow rewrite. Local-first first, cloud-expandable when you need it.

Status: DEV linux-native backend (partial) · PLANNED hosted Linux target

Notes

  1. Full Linux VM per sandbox on Apple Virtualization.framework; macOS 14+ (Sonoma) required for VM state save/restore.
  2. Boot and reuse behavior as stated in the vz repository documentation (v0.3.20): ~3 s typical cold boot to first command; setup cached by hash; warm reuse instant. Subject to the project's measured-claims policy; no independent benchmark is claimed here.
  3. Architectural invariant: the host executes only the CLI, the vz-runtimed control daemon, and vsock/VirtioFS plumbing; every workload, including dockerd in revision F.2, executes inside the guest VM.
  4. Agent interface register follows the vz agent-sandbox API landscape survey (MCP tool set, §7.5); MCP server implementation is PLANNED (rev F.3). Underlying primitives carry their own statuses.
  5. Guest kernel 6.12.85, profiles developer (nested virt) and container (constrained: seccomp, netns, overlayfs, btrfs snapshots).
