Features

  • ▪Environment first. Each isolated project instance owns a topology of target-native Machines
  • ▪Linux everywhere. Linux-on-macOS now; Linux-on-Linux next; Linux-on-Windows later
  • ▪Native where it matters. macOS-on-macOS now; Windows-on-Windows follows Linux-on-Windows
  • ▪Docker is implicit for Linux development. Each Developer-profile Linux Machine owns a private Engine, context, state, and cache
  • ▪Parallel on both axes. Many isolated Environments per project; many cooperating Machines per Environment
  • ▪Public-like, still local. Declared DNS, TLS, ingress, NAT, firewall, and network faults without accidental exposure (PLANNED)
  • ▪Honest capabilities. Host×Machine-target support is ACTIVE, DEV, PLANNED, or NA, exactly as the checked-in capability matrix says
  • ▪Hardened when requested. Lockdown remains a secondary profile, not the product center

1 · General description

vz creates reproducible, parallel Developer Environments on local hardware. A project defines a topology that can be instantiated many times; each isolated Environment contains one or more target-native Machines plus its storage, networks, endpoints, policies, and lifecycle.

Linux is the universal Machine target. Linux and native macOS Machines can coexist in one Environment on macOS; Linux moves next to Linux hosts and later Windows, with native Windows last.

Every Developer-profile Linux Machine includes private Docker readiness: its own Engine, containerd, BuildKit cache, images, volumes, networks, endpoint, and managed context. There is no Environment-wide/global socket and no fallback to Docker Desktop, a sibling Machine, or another Environment.

Current runtime and VM mechanisms are real; the five-verb vz up/exec/status/stop/delete lifecycle, topology fabric, and full host-Docker-CLI parity remain in development.

  • ACTIVE Shipped in the published target release AND retained installed evidence exists for the exact host×target×profile pair. Requires non-empty evidence.
  • DEV Implemented and demonstrated by an installed local-Mac slice that is not release certified. Requires non-empty evidence.
  • PLANNED Committed direction with no negotiation path. Requires empty negotiated_by, rejected_by and evidence.
  • NA Explicitly rejected by validation as an unsupported pairing or declaration. Requires non-empty rejected_by.

Source of truth: config/host-target-capabilities-v0.4.json in the repository. No entry is labelled shipped until a 0.4 release is published.

5Detailed description

Clauses 5.1 – 5.6
5.1Project, Environment & Machine identity

A ProjectDefinition may create many Environment instances, including several for one worktree. Each Environment owns a topology of Machines; each Machine owns its immutable target specification and target-native state. Unsupported host/Machine-target pairs fail explicitly.

Status: DEV Linux and native macOS Developer Machines on Apple silicon · NA Hardened native macOS
5.2Machine targets & topology

On macOS, Linux and native macOS Machines can form one Environment through declared private or simulated-public paths. Linux OCI execution uses pinned youki; the same Linux Machine contract moves next to Linux and Windows hosts.

# 0.4 Developer Environment lifecycle (DEV)
vz up --environment demo
vz status --environment demo --json
vz exec --environment demo --machine api -- make test
vz stop --environment demo
Status: DEV youki-only runtime in Developer Linux Machines · PLANNED deny-first Environment networking
5.3Docker compatibility belongs to Linux

Every Developer-profile Linux Machine owns a private dockerd, containerd, BuildKit cache, images, volumes, networks, endpoint, and context. The host Docker CLI selects that exact Environment/Machine. No Environment-wide/global socket, default-context mutation, fallback, or cross-routing is allowed.

# use the Machine context reported by vz status
docker --context vz-agent-a-api ps
docker --context vz-agent-a-api compose up
docker --context vz-agent-a-api build -t app .
Status: DEV implicit Engine, Compose, buildx and managed context per Developer Linux Machine; full host-client parity is not release certified
5.4Native macOS Machine

Native macOS Machines reuse pinned images, provisioning, guest-agent execution, patching, and save/restore. They can communicate with declared Linux Machines but never inherit their Docker capability.

Status: DEV native macOS Developer Machine lifecycle, exec and PTY · NA Docker on native macOS
5.5Parallelism, network & persistence

Many Environment instances and many Machines run concurrently. Separate Environments share no mutable state or routes. Machines use declared paths, including a local public-like DNS/TLS/ingress/NAT edge. Stop preserves declared state; delete removes only the selected ownership graph.

Status: DEV Environment ownership, Stop and Delete · PLANNED public-like edge, snapshots and checkpoints
5.6Platform expansion

The ordered Machine-target matrix is Linux-on-macOS and macOS-on-macOS now; Linux-on-Linux next; Linux-on-Windows later; Windows-on-Windows finally. Linux remains portable; native Machines preserve their operating-system semantics.

Status: DEV Apple-silicon macOS host · PLANNED Linux hosts · PLANNED Windows hosts

7Host × Machine-target truth table

Linux universal · native additive

Support is earned per host×Machine-target pair. Linux travels across all hosts; native Machines are added where their operating-system toolchains matter.

HostTargetStatus and contract
macOSLinuxDEV lifecycle, exec and private Developer-profile Docker · PLANNED topology networking
macOSmacOSDEV Developer Machines with exec and PTY · NA Hardened profile
LinuxLinuxPLANNED partial native backend in the tree; no Machine target resolves on a Linux host
WindowsLinuxPLANNED universal Linux contract through a Windows virtualization backend
WindowsWindowsPLANNED native Windows Developer Machines after Linux-on-Windows
Docker is implicit only for Developer-profile Linux Machines. Each owns a private Engine, containerd, BuildKit cache, images, volumes, networks, endpoint, and context. Hardened Linux Machines omit Docker; native macOS/Windows Machines do not receive a hidden Linux sidecar or Docker service.

Notes

  1. The current Linux-on-macOS backend uses a Linux VM on Apple Virtualization.framework; native macOS environments use macOS VMs. macOS 14+ (Sonoma) is required for VM state save/restore.
  2. Boot and reuse behavior as stated in the vz repository documentation (v0.3.20): ~3 s typical cold boot to first command; setup cached by hash; warm reuse instant. Subject to the project's measured-claims policy; no independent benchmark is claimed here.
  3. For Linux-on-macOS, Linux workloads—including each Developer-profile Linux Machine's future private dockerd—execute in that Machine's backend. Hardened Machines do not gain implicit Docker. Declared host clients and bridges remain visible parts of the contract.
  4. The typed API register in §4 is proposed. The repository skill documents the five-verb surface; convergence is DEV.
  5. Guest kernel 6.12.85 currently builds developer and legacy container profiles; the public restricted profile becomes Hardened.
